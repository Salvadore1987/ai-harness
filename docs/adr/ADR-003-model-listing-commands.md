# ADR-003. Команды `ps` и `list`: загруженные и установленные модели

- **Статус:** принято
- **Дата:** 2026-10-29
- **Контекст:** ADR-001 (п. 1, 5), ADR-002, запрос «добавить команду `ps` для вывода запущенных
  моделей и `list` для вывода всех имеющихся моделей»

## Контекст

Список установленных моделей в harness был только у `/model` без аргумента, внутри REPL.
Загруженные модели не показывались никак: чтобы узнать, какая модель занимает память, с каким
окном контекста она загружена и когда Ollama её выгрузит, приходилось переключаться на
`ollama ps`. Для harness эти данные важны: окно контекста, по которому считается компакция,
берётся из `GET /api/ps` (`OllamaContextBudgetAdapter`), а не из настроек.

`ollama ps` и `ollama list` не заменяют встроенные команды. Им нужен Ollama CLI на той же
машине, они ничего не знают о `HARNESS_OLLAMA_BASE_URL` и `text-json`-режиме, а их текстовый
вывод неудобно разбирать.

## Решения

### 1. Две точки входа с одной логикой

| Где | Команды | Поведение |
|---|---|---|
| REPL | `/list [префикс]`, `/ps [префикс]` | Печатают таблицу, REPL продолжает работу; ошибка печатается, как у других slash-команд |
| CLI | `harness list [PREFIX]`, `harness ps [PREFIX]` | Печатают таблицу и выходят: код 0, при ошибке — 1 |

Подкоманды CLI удобны в скриптах и не открывают сессию: корневая `HarnessCommand` при
подкоманде не выполняется, поэтому сессия не создаётся и модель не проверяется. `/model` без
аргумента остаётся и печатает ту же таблицу, что `/list`.

### 2. Подкоманды picocli — Spring-бины, подключаются через `addSubcommand`

ADR-001 (п. 5) откладывал собственную `IFactory` до появления подкоманд. Она не понадобилась:
`ListModelsCommand` и `RunningModelsCommand` — `@Component` с внедрением через конструктор,
`PicocliRunner` получает их как бины и подключает готовые экземпляры:
`new CommandLine(command).addSubcommand(list).addSubcommand(ps)`. Аннотация
`@Command(subcommands = …)` не используется: тогда picocli создавал бы классы сам, в обход
Spring. Тесты собирают `CommandLine` так же (`CliTestContext.commandLine()`).

### 3. Ядро: новый порт для загруженных моделей, `list` переиспользует существующий запрос

- `list` — существующий `ListModelsQuery` и `ModelCatalogPort`, без изменений.
- `ps` — новые `RunningModelsPort` (выходной порт), `ListRunningModelsQuery` и
  `ListRunningModelsQueryService` (входной порт и use case), `ListRunningModelsCriteria`
  (фильтр по префиксу) и `RunningModelResult`. Конвертацию в результат делает
  `TurnApplicationMapper`.

Загруженные модели получили отдельный порт, а не метод в `ModelCatalogPort`. Каталог описывает
установленные модели и работает через `OllamaApi` из Spring AI, а `/api/ps` Spring AI не
покрывает. У них разные источники и разное поведение при ошибке, а фейкам каталога в тестах не
нужно знать про загруженные модели.

### 4. Адаптер: общий клиент `/api/ps`

`OllamaPsClient` — единственное место, где вызывается `GET /api/ps`. Им пользуются два адаптера
с разной реакцией на ошибку:

| Адаптер | Порт | При недоступной Ollama |
|---|---|---|
| `OllamaContextBudgetAdapter` | `ContextBudgetPort` | Берёт `harness.context.num-ctx` и пишет в лог |
| `OllamaRunningModelsAdapter` | `RunningModelsPort` | Бросает `LlmUnavailableException` / `LlmResponseException` через `OllamaErrorTranslator` |

DTO `OllamaRunningModels.RunningModel` дополнен полями `size`, `size_vram` и `expires_at`.
Записи без имени пропускаются, отсутствующие размеры становятся нулём
(`RunningModelOllamaMapper`, MapStruct).

### 5. Представление: общий `ModelListPrinter`

Обе точки входа печатают через один компонент, поэтому формат совпадает.

- **`ps`** — колонки как у `ollama ps`: модель, размер в десятичных GB, процессор (`100% GPU`,
  `100% CPU` или `48%/52% CPU/GPU` по `size_vram / size`), окно контекста и время до выгрузки
  («через 29 мин», «через 3 ч 15 мин»). При `keep_alive: -1` Ollama ставит дату выгрузки через
  сотни лет — такой срок показывается как «бессрочно».
- **`list`** — колонки harness, а не `ollama list`: параметры, квантование, `thinking`/`tools`.
  Для выбора модели в агентном режиме возможности важнее размера файла и даты изменения.
  Звёздочкой отмечена текущая модель (в REPL) или модель по умолчанию `harness.model` (в CLI).

## Рассмотренные альтернативы

| Вариант | Почему нет |
|---|---|
| Только slash-команды | Нельзя использовать в скриптах без запуска REPL |
| Только подкоманды CLI | Внутри REPL пришлось бы выходить из сессии |
| Запускать `ollama ps` / `ollama list` процессом | Нужен Ollama CLI локально, не работает с удалённой Ollama, текстовый вывод пришлось бы разбирать |
| Метод `listRunning()` в `ModelCatalogPort` | Смешивает два источника с разной реакцией на ошибку, см. п. 3 |
| `@Command(subcommands = …)` + своя `IFactory` поверх `ApplicationContext` | Лишний код: `addSubcommand` с готовыми бинами решает задачу |

## Последствия

- Видно, какая модель занимает память, сколько её на GPU, с каким окном она загружена и когда
  выгрузится, — без выхода из harness и без Ollama CLI.
- Native image: `OllamaRunningModels` уже зарегистрирован в `NativeHintsConfig`
  (`BindingReflectionHintsRegistrar` обходит вложенные типы), команды picocli описывает
  `picocli-codegen`. `NativeImageSmokeIT` проверяет `harness list`, `harness ps` (включая
  `expires_at` с часовым поясом), `/list` и `/ps` в бинарнике. `harness ps` против локальной
  Ollama отвечает за 0.06 с (без MCP-серверов).
- `list` по-прежнему делает `POST /api/show` на каждую установленную модель, чтобы узнать
  возможности; с десятками моделей команда заметно медленнее `ps`.
- MCP-серверы подключаются в фоне по `ApplicationStartedEvent` и при запуске подкоманды:
  процессы stdio-серверов стартуют и закрываются вместе с приложением, предупреждения о них не
  печатаются. Если это станет заметно, подключение можно отложить до первого запроса
  инструментов.
