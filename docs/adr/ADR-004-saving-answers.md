# ADR-004. Сохранение ответа в файл: `/save`, `save_answer` и перенаправление `-p`

- **Статус:** принято
- **Дата:** 2026-10-30
- **Контекст:** ADR-001 (п. 1, 3), ADR-002, запросы «перенаправлять поток в файл markdown»,
  «при `-p` файл создаётся, но текста нет», «добавить `/save`; когда я говорю „сохрани данный
  текст“, не перегенерировать его, а просто сохранить в файл»

## Контекст

Сохранить ответ модели в файл было нельзя ни одним надёжным способом:

- `harness -p "…" > answer.md` создавал пустой файл, ответ печатался в консоль.
- В REPL не было команды сохранения, а перенаправить вывод изнутри REPL нельзя.
- В режиме `agent` на просьбу «сохрани этот текст в файл» модель вызывала `write_file` и
  генерировала текст заново. Это тратит токены, а длинный ответ получается не дословным.

Ответы уже хранятся дословно в истории сессии (`~/.harness/sessions/<id>.jsonl`), так что
повторно генерировать их не нужно.

## Решения

### 1. Терминал JLine привязан к stdout

`TerminalBuilder` по умолчанию (`SystemOutput.SysOutOrSysErr`) переключается на stderr, когда
stdout перенаправлен, а stderr ещё подключён к терминалу. Из-за этого ответ при `-p … > file`
уходил в консоль. Теперь в `TerminalConfig` задано `systemOutput(SystemOutput.SysOut)`. При
перенаправленном stdout создаётся dumb-терминал поверх stdout: ответ попадает в файл без
ANSI-кодов, строка «✻ размышлял …» и вызовы инструментов, как и раньше, идут в stderr.

### 2. Один сценарий — две точки входа

| Где | Как | Какой ответ сохраняется |
|---|---|---|
| REPL | `/save [файл]` | Последний ответ сессии |
| Агент | инструмент `save_answer(path?)` | Последний ответ **до** текущего запроса пользователя |

Обе точки входа вызывают `SaveAnswerUseCase` (`SaveAnswerService`) с командой
`SaveAnswerCommand(sessionId, workingDirectory, path, skipCurrentTurn)`. Агенту текущий ход
нужно пропустить: ответ на просьбу «сохрани» ещё не готов, а нужен текст, который пользователь
видел, когда просил. `/save` выполняется между ходами, поэтому ничего не пропускает.

Режим `chat` не получил инструментов: там по-прежнему работает только `/save`. Угадывать
намерение «сохрани» по тексту сообщения ненадёжно, а включение инструментов в чате изменило бы
смысл режима.

### 3. Какой ответ считается «последним»

- Это последнее сообщение ассистента с непустым текстом. В агентном ходе это финальный ответ,
  а не реплики перед вызовами инструментов.
- Ходы, в которых вызывался `save_answer`, пропускаются: их ответ только подтверждает
  сохранение. Поэтому «сохрани ещё и в другой файл» и `/save` после сохранения агентом
  записывают тот же текст, а не «Сохранено в …».
- Ответ, прерванный отменой или обрывом соединения, сохраняется с той же пометкой, с которой
  он хранится в истории.
- Если подходящего ответа нет, в том числе после компакции, которая заменила его сводкой,
  бросается `AnswerNotFoundException` (код `300004`). В REPL `AnswerErrorHandler` печатает
  «Сохранять нечего», агент получает текст ошибки как результат инструмента.

### 4. Файл

- Путь считается от рабочей директории (`--cwd`); недостающие папки создаются, существующий
  файл перезаписывается, как в `write_file`.
- Без имени или с именем существующей папки файл называется `answer-<yyyyMMdd>-<HHmmss>.md`
  по локальному времени. Время берётся из общего бина `Clock`.
- Запись выполняет новый выходной порт `AnswerFilePort` (адаптер `out/file/AnswerFileAdapter`).
  Так сервис не зависит от файловой системы, а в тестах её заменяет `InMemoryAnswerFilePort`.

### 5. Инструменты получают сессию

Чтобы `save_answer` знал, из какой истории брать ответ, `ToolExecutorPort.execute` принимает
`SessionId`. `SpringAiToolExecutorAdapter` кладёт его в `ToolContext` под ключом `sessionId`
рядом с рабочей директорией, а `ToolContexts.sessionId()` читает его. Имя инструмента задаёт
константа `SaveAnswerUseCase.TOOL_NAME`: по ней же сервис узнаёт ходы с сохранением.
`AnswerTools` строит команду через MapStruct-маппер `AnswerToolMapper`.

### 6. Подсказка модели

В системный промпт агента и в описание `save_answer` добавлено правило: текст, уже написанный
в этом разговоре, сохраняется через `save_answer` и никогда не перепечатывается через
`write_file`. На `qwen3.5:27b` в новой сессии модель выбирает `save_answer` стабильно,
файлы совпадают с ответом побайтово. В сессии, где модель раньше уже сохраняла текст через
`write_file`, она продолжает повторять этот вызов из истории. Для таких сессий остаётся
`/save`.

## Рассмотренные альтернативы

| Вариант | Почему нет |
|---|---|
| Второй адаптер `TurnOutputPort`, который дублирует поток в файл (`--output`, `/record`) | Нужен для записи во время генерации; для «сохранить готовый ответ» сложнее и требует менять порт, чтобы в файл попадал вопрос. Остаётся возможным расширением |
| Экспорт всей сессии в markdown (`/export`) | Решает другую задачу — сохранить диалог целиком; можно добавить поверх того же чтения истории |
| Просить модель повторить ответ и перенаправлять `-p` | Повторная генерация: тратит токены, текст не дословный |
| Распознавать «сохрани …» в тексте сообщения без участия модели | Ненадёжно и неочевидно для пользователя |
| Отдельный порт чтения истории для инструмента в обход сценария | Дублирует логику выбора ответа; инструмент и `/save` разошлись бы |

## Последствия

- Сохранение не обращается к модели и работает в обоих режимах REPL; в агентном режиме — и по
  просьбе словами.
- Сигнатура `ToolExecutorPort.execute` изменилась: фейки и тесты инструментов передают
  `SessionId`.
- Native image: `AnswerTools` зарегистрирован в `NativeHintsConfig` вместе с остальными
  классами `@Tool`. Без этого `save_answer` не нашёлся бы в бинарнике.
- `/tools` показывает `save_answer` как встроенный инструмент.
